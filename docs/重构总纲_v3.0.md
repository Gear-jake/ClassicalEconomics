## 一、诊断：三个用户痛点，根因已定位到行

### 痛点 1：禁用一切后仍「无穷无尽的夺权叛乱」

社区反馈原文：「这个 mod 会导致世界在禁止自由决策和叛乱的情况下依然发起无穷无尽的夺权叛乱和内战」（五百川文蛾）、「设置里能禁的都禁了，还是会莫名一直政权更替」（mirukuti）。

**根因 A —— 政策引擎不看总开关**

~~~csharp
// Core/PolicyEngine.cs:65
var cfg = UnrestConfig.Instance;
if (!cfg.PolicyEnabled) return;      // ← 只检查 policy_enabled，不检查 cfg.Enabled(unrest_enabled)
~~~

玩家把「社会动荡」关掉后，`UnrestEngine.Evaluate()` 会在 `:72` 因 `!cfg.Enabled` 返回，**但 `PolicyEngine.Evaluate()` 照常每年运行**。两个开关语义重叠却没有父子关系。

**根因 B —— 内战绕过动荡引擎的门禁**

`FailPolicy` 的第三个分支（`PolicyEngine.cs` 内战路径）直接调用 `UnrestEngine.TriggerCivilWar(kingdom)`，**跳过了 `Evaluate()` 里的 `cfg.Enabled` 判断**。所以即使关掉动荡，强制内战依旧触发。

**根因 C —— 没有任何「政权更替」粒度开关**

`policy_enabled` 一个开关同时控制「改革（降基尼，好事）」和「失败后果（退位/驾崩/内战）」。作者自述：「政权变更是经济崩溃基尼指数过高导致的，**本身我好像没给开关**」。玩家想要的是「我要改革，但不要换王」——现在做不到。

**根因 D —— 频率确实过高**

| 参数 | 现值 | 位置 |
|---|---|---|
| 触发阈值 | 基尼 **≥ 0.6** | `PolicyEngine.cs:26 PolicyGiniThreshold` |
| 每年尝试率 | **35%** | `:29 AttemptChance` |
| 成功率 @基尼0.75 | ≈ 54%（失败 46%） | `:150 RollSuccess` |
| 失败后果 | **40% 退位 / 30% 驾崩 / 30% 内战** | `FailPolicy` |
| 失败冷却 | 仅 **6 年** | `:32 CooldownYears` |

推算：基尼 0.6 以上的王国约 **2.9 年尝试一次**，失败间隔约 6 年，其中 70% 导致政权更替 → **单个王国平均 9 年换一次政权**。一个 20 国的世界，每年期望 2 次政权更替——玩家观感就是「无穷无尽」。

**根因 E —— 未尊重原版设置（待核实）**

mod 用 `Kingdom.addTrait` + 原生 `startRebellion` 体系，理论上应受原版「自由决策/叛乱」开关约束；但强制内战路径 `TriggerCivilWar` 是主动调用，需要核实它是否读取原版开关。**这是「禁止叛乱却仍内战」的最可能解释。**

### 痛点 2：卡顿

| 项 | 现状 | 证据 |
|---|---|---|
| 实时刷新同步算 | 每 5 秒主线程做全量采集 + **O(N log N) 基尼排序** | `EconomyModMain.RealTimeRefresh`（W3-A/B 未做） |
| 年末尾帧尖峰 | `Snapshot` 阶段**豁免帧预算**，全部经济阶段完成后同帧收尾 | `AnnualPipeline.Tick` |
| UI 销毁重建 | 每次刷新 100–250 个 GameObject 销毁重建，**每 5 秒一次** | `FloatingWindow.ClearContent` 路径 |
| 语言常驻 | 6 个语言文件 **1.55 MB** 全量常驻 | `LocalizationService` 静态 6 字典 |
| 年度全量扫描 | 优化前 6–8 次/年；已融合为 1 次（W2-A 已做） | ✅ 已改善 |

### 痛点 3：UI「廉价塑料」

现方案是**自建 Canvas + 自定义美术**：`UIStyles` / `UIArt` / `UIHelpers` / `UIComponents` 全套自绘，配色、圆角、字体与游戏本体没有任何血缘关系。其他模组「甚至就用原版面板」。

**已验证可行的替代路径**：0.51 平台的 `NeoModLoader.dll`（1.2.0.1，22.5 MB）中**确实包含**原版风格窗口框架：

```
AutoLayoutWindow          ✓
SingleAutoLayoutWindow    ✓
MultiTabWindow            ✓
AutoLayoutGroup           ✓
WindowLibrary             ✓
ScrollWindow              ✓（本体 17 处引用）
SimpleButton              ✓
ModPowerTabFeature        ✓
```

即：**可以不改游戏资源，直接获得原版外观**。工作量集中在把现有 5 个窗口从自绘 Canvas 迁到这些基类。

### W2 —— UI 全面重构（**最大工作量**）

#### ⚠ 关键约束（用户 2026-10-07 明确）：**不能用原版窗口容器**

已在反编译源中确证暂停机制：

```csharp
// 共用游戏源码\ilspy\decomp\base\MapBox.cs:1692
_is_paused = Config.paused || ScrollWindow.isWindowActive() || RewardedAds.isShowing();

// ScrollWindow.cs:41 / :125
private static ScrollWindow _current_window = null;
public static bool isWindowActive() => _current_window != null;
```

**只要有任何 `ScrollWindow` 系窗口处于激活状态，游戏就暂停**。而原版窗口（`WindowLibrary` / `AutoLayoutWindow` / `MultiTabWindow`）全部派生自它。

**因此路线修正为：保留「不暂停的悬浮容器」，只换「本体视觉皮肤」。**

| 保留 | 替换 |
|---|---|
| `FloatingWindow` 自建 Canvas 容器（不注册为 `ScrollWindow` → `isWindowActive()` 恒为 false → **游戏不暂停**） | 自绘美术层 `UIStyles` / `UIArt` / 自绘 sprite —— 换成**游戏本体 UI 素材** |
| 自带刷新节拍（挂在 `EconomyTickRunner` 上，与游戏运行解耦） | 配色 / 边框 / 字体 —— 对齐本体 |

**已验证可用的本体 UI 素材**（`SpriteTextureLoader.getSprite(path)`，58 条路径）：

## 三、关于「多核计算」的可行性判断

| 可以并行 | 不可以并行 |
|---|---|
| `TradeSimulationWorker` 的**纯数值计算**（贸易流、基尼排序、王国聚合）——已是后台线程，可进一步按王国 id 分片跑 `Parallel.For` | 任何触碰 `Actor`/`Kingdom`/`City`/Unity 对象的采集（**必须主线程**） |
| `DecisionEvents` 的 O(K×E) 条件求值（只读 `_defs` 与纯数值快照） | 写世界状态的效果执行（`addTrait`/`startRebellion`/金币变动） |
| 语言文件解析、事件定义解析（初始化期） | UI 构建（Unity 限制） |

**结论**：值得做，但**优先级低于 4.3/4.4**（实时异步化）。当前瓶颈在主线程同步算基尼，不在核数。建议：**先异步化，再并行化**——否则并行只会把同样的阻塞摊到更多核上。

## 四、建议执行顺序与依赖

~~~
W0 门禁分层  ← 前置，零风险，必须先做
   ↓
W1 紧急修复（崩溃/政权更替开关 + 降频）  ← 用户最痛，可先出 hotfix
   ↓
W4.3 / W4.4 实时异步化  ← 卡顿主因，改动可控
   ↓
W2 UI 全面重构  ← 最大工作量，建议单独排期
   ↓
W3 结构收敛  ← 在 UI 与性能稳定后进行，避免同时移动太多东西
   ↓
W4 其余 + W5 收尾
~~~

**关键路径**：W0 → W1 → W4.3 → W4.4 → W2 → W3 → W5。

> 排序理由：W1 改动最小、用户痛感最强，先稳住；W2（UI）工作量最大且会大面积触碰文件，必须在门禁分层（W0）之后、结构收敛（W3）之前做，否则两次大搬家会互相打架。
>
> **发布节奏（用户 2026-10-07 确认）：不单独发 hotfix，攒到一个版本一起发。** W1 的修复与 W2/W3/W4 同批交付；发布前必须全量门禁 + 行为一致性 + 4 档性能矩阵全绿。
