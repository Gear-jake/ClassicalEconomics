## 五、要不要重构：核心判断

### 判断一：**性能**不用重构，把 v2.1.0 计划做完即可

剩余四项（W1-D / W1-F / W3-A/B / W4）都是**局部改造**，计划里已经写明了做法、验收、语义风险与缓解。继续执行比重新设计便宜得多。

### 判断二：**结构**重构的最大障碍不是代码，是门禁

这是最关键的发现。你的 48 个门禁是**源码正则断言**——`优化计划_v2.1.0.md` §0.2 明确列出「必须逐字保留」清单：

- 方法签名与区域锚点：`public static void ApplyWealthTax(` → `private static void UpdateTopRich(`
- 字段名：`_pendingYear` / `_lastCollectedYear` / `_cyclePending`
- 常量值：`MaxAttackersPerVictim = 16`、`FrameBudgetMs = 4`、`HardWindowMs = 5000L` …
- **连注释文本**：`consumption(spending) -> banking -> other`、`the wealth-tax/redistribution path is never reduced (tax conservation)`

**含义**：任何重命名、拆文件、移常量、改注释，都会先打红一批门禁。重构的第一步不是改代码，而是**改门禁**。

好消息是地基已经在了：`PerfCounters`（可测）+ `Test-BehaviorParity`（黄金哈希，行为等价）+ 金币守恒不变量 —— 这三样足够把门禁从「形状断言」升级为「行为断言」。

### 判断三：**两条经济线不应该合并**

| 理由 | 说明 |
|---|---|
| 平台不同 | 719（Unity 2022.3 + NML 1.2 新体系）vs 558（Unity 2020.3 + 本体版 NML） |
| 定位不同 | 观察层 vs 接管层；接管层在 719 上要面对完全不同的原版经济代码 |
| 存储不同 | 王国 data 键 vs 外部 SQLite；迁移成本高、收益低 |
| 用户群不同 | 一个是 Steam 创意工坊的成品，一个在 558 生态 |

**该共享的是「纯工具」，不是「经济模型」** —— 这正是 `mod-suite-architecture.md` 已经写下的结论。

## 六、建议路线（如果决定动手）

### Phase 0 —— 先重构门禁（**前置，零功能风险**）

1. 门禁分两层：**行为层（硬门禁）** = 金币守恒 / 黄金哈希 / 特质计数 / 管线顺序不变量；**形状层（软 lint）** = 现有的源码正则断言，允许形状变化但需人工确认差异。
2. 补一条「重构安全网」：`Test-*` 跑完后自动跑 `Test-BehaviorParity`，行为不一致即 RED。
3. 产出 `docs/门禁分层说明.md`，明确哪些断言是契约（不可变）、哪些是形状（可变）。

> **做完 Phase 0 之前，不要开始任何结构性重构。** 否则你会在「改代码 → 门禁红 → 改回代码」的循环里空转。

### Phase 1 —— 低风险边界收敛（不碰引擎内部）

| 动作 | 收益 | 风险 |
|---|---|---|
| 拆巨型文件：`EconomyHUD`(1275) / `CabinetWindow`(1137) / `DecisionEvents`(1123) 按「视图 / 逻辑 / 数据」三层拆 | 可读性、AI 可导航性大幅提升 | 低（纯移动 + 同名转发） |
| 配置五向一致 → 单一来源生成 | 新增 1 个配置键从改 5 处变成改 1 处 | 低 |
| 存档键收敛：`rb_*` 分散在 `NationSave` / `LawSave` / `DecisionEvents` → 统一 `SaveSchema` 常量表 | 存档格式可审计、防键冲突 | 低 |
| 4 处补丁安装收敛为统一 `PatchInstaller` + 逐补丁 try/catch + `docs/patches.md` 登记表 | 冲突可审计 | 低 |

### Phase 2 —— 跨模组共享核心（对齐你自己的套件计划）

按 `mod-suite-architecture.md` 的 P1：建 `工程\共用模组核心\`，用 **源码链接**（不是共享 DLL）抽取纯工具：`Logger` / `ConfigLoader` / `WorldId` / `FrameScheduler` / `PerfDiagnostics` / `TryCatchGuard` / `PatchRegistrar` / `LocaleMerge`。

**优先抽 `WorldId` 与 `FrameScheduler`** —— 这两样在两个经济模组里各写了一遍，且都踩过坑（世界 ID 丢失导致钱归零 / 年度卡顿），共享后只需修一处。

### Phase 3 —— 性能收尾

把 v2.1.0 的 W1-D / W1-F / W3-A/B / W4 做完，用已有的 `PerfCounters` + `PerfCapture.ps1` 出前后对比。

## 七、明确不建议做的事

| 不要做 | 原因 |
|---|---|
| 不要把 33 个引擎合并成「大 EconomyEngine」 | 它们对应 17 个管线阶段，拆分是刻意的；合并会让帧预算切片失效 |
| 不要改 `AnnualPipeline` 的阶段顺序或语义 | 顺序本身是不变量（税收守恒依赖它） |
| 不要把存档从「王国 data 键」换成 SQLite | 719 上现方案已稳定；换存储是纯风险 |
| 不要为「架构优雅」引入 DI / 事件总线 / 接口抽象层 | 这是单一职责的模组，抽象层只会增加间接跳转与排查成本 |
| 不要重写 `BankingEngine` | v2.1.0 计划里已明确「本方案完全不碰此文件」 |
| 不要在 Phase 0 之前重命名任何被正则锚定的标识符 | 会直接打红门禁 |

## 八、需要你拍板的三个问题

1. **重构目标是什么？** —— 是「我要能继续加功能不痛苦」（→ Phase 0+1 就够），还是「我要把两个经济模组统一成一套」（→ 那是另一个量级的项目，且我判断不该做）？
2. **v2.1.0 剩余四项还做不做？** —— W1-D / W1-F / W3-A/B / W4 都已有明确方案，做完即闭环。
3. **要不要先做 Phase 0（门禁分层）？** —— 这是所有结构重构的前置条件，且**零功能风险**，我建议无条件先做。
